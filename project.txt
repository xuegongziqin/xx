我的方案：
# **程序存活竞赛方案设计文档**

## 1. 项目概览

| 模块名称              | 类型      | 功能定位                                                |
| ----------------- | ------- | --------------------------------------------------- |
| **xx.exe**        | 主进程     | 用户态入口，加载守护模块与攻击模块，维护日志中心                            |
| **svcguard.dll**    | 守护模块    | 自我复活与扩散（仅本会话），部署 guard.dll 宿主并交接 xx 进程句柄，按心跳计数器复活 xx |
| **window.dll**    | 弹窗与日志模块 | 显示全局日志并证明程序存活，支持多进程冗余与自动重建                          |
| **atkcore.dll** | 攻击工具箱   | 提供动态调用接口，对对方进程执行结束操作                                |
| **payload.dll**    | 攻击载荷    | 注入对方进程执行自定义载荷（结束自身进程）                            |
| **guard.dll**     | 进程看门狗   | 由 svcguard 注入宿主进程运行（xx 不加载自己），读取 xpt.xpt，监控并复活受保护进程、恢复被挂起线程 |
| **defense.dll**   | 合并防御模块  | 合并 xx 原有防御与新 yy 的防御：敌人文件锁/设备锁/VEH自愈/LdrLoadDll反注入/心跳看门狗 |

---

## 2. 核心策略

1. **弹窗存活优先**

   * 胜负判定依据 `window.dll` 弹窗是否连续消失 8 秒。
   * 采用多进程冗余机制，确保窗口至少有一个实例存活。

2. **DLL 自我扩散**

   * 每 500ms 扫描**本会话**进程，向新进程注入自身（注入结果缓存 10s）。
   * 旧的 DLL 自动退出释放资源，防止资源泄漏。

3. **守护与复活机制**

   * 弹窗存活判据 = 共享内存心跳计数器：持有弹窗的 `window.dll` 实例每 500ms 递增一次，能看到本桌面弹窗的热备实例也帮忙递增。
   * `svcguard.dll` / `defense.dll` 每 500ms 轮询该计数器，连续 2.5 秒不涨即尝试复活 `xx.exe`（命名互斥锁串行化，已有实例在跑则跳过；不再自我卸载）。
   * `window.dll` 通过 `Local\xx_window_guard`（单会话）互斥锁热备；抢不到锁时若本桌面 1.5 秒看不到任何 XX 弹窗，就无视锁强建弹窗。
   * 弹窗被关闭或宿主进程被结束时，快速在其他宿主进程重建。

4. **攻击能力**

   * `atkcore.dll` 提供 5 种用户态进程结束方法：

     1. TerminateProcess
     2. CreateRemoteThread + ExitProcess
     3. 注入 `payload.dll`
     4. 注入 `payload.bin`（位置无关 shellcode，可绕过签名检查）
     5. Job 对象终止
   * `payload.dll` 执行自定义载荷逻辑，按需加载。

## 3. 模块详细设计

### 3.1 xx.exe（主进程）

* 进程入口先提权：`EnableDebugPrivilege` 启用 `SeDebugPrivilege`（`AdjustTokenPrivileges`），供跨进程句柄打开、注入与击杀使用。
* 一运行就创建 3 个线程：
  1. `AttackThread`：加载 `atkcore.dll` 并调用 `StartAttack`，同时定向关闭 `yy.exe` / `ww.exe` 窗口并重建同名假窗口。
  2. `InitThread`：设置安全描述符 → 初始化/接管共享内存（写布局版本与启动 tag，沿用或生成心跳/窗口后缀）→ 加载 `svcguard.dll` → 加载 `window.dll`（刻意排在 WMI 之前）→ 写 `xpt.xpt` → 创建 WMI 永久订阅 → 加载 `defense.dll`（`guard.dll` 改由 svcguard 注入宿主，不在 xx 内加载）。
  3. `SelfProtectThread`：持续维护 `xxres.bin` 自身备份，供文件被删后还原。
* 提供全局日志服务，供 `window.dll` 显示。
* 内置自我保护逻辑，尝试恢复已被结束的子模块。

### 3.2 svcguard.dll（守护模块）

* 进程入口先提权：`EnableDebugPrivilege` 启用 `SeDebugPrivilege`。
* 每 500ms 扫描**所有会话**的进程并注入（注入结果缓存 10s）。**不要**按会话过滤扩散：xx 与目标进程会话不一致时（服务/SYSTEM 启动、RDP、多用户）会一个都注不进去，表现就是"别的进程里没有我们的 dll"。会话限制只放在**复活**：只允许在 xx 原先的会话里拉起 xx.exe。
* 每 10 秒输出扩散统计，成功注入记名，`OpenProcess` 失败带 err 码 —— 弹窗日志里就能看出注入是否发生。
* 反"反注入"：注入前先还原目标进程里被改写的 `ntdll!LdrLoadDll` 前导字节（原始字节取自磁盘 ntdll 的 SEC_IMAGE 映像，避免照抄自己被 defense hook 过的字节），并用远端线程退出码校验 LoadLibrary 是否真的成功 —— 否则对手按名拦截我们 dll 时会被误判成"注入成功"。
* 以 `access=0 + FILE_SHARE_READ` 持锁保护我方文件（xx.exe / 各 dll / xxres.bin）：Windows 允许删除运行中的镜像，不锁的话对手删掉文件后新的注入就无源可注。该共享模式实测能锁住运行中的镜像、挡住删除/改名/覆盖写入，同时仍允许读取与 LoadLibrary。
* 跳过关键系统进程（`IsProtected` 黑名单，含 `notepad.exe`）。
* 心跳计数器连续 2.5 秒不涨即 `RespawnXX`（命名互斥锁 `Global\xx_respawn_guard` 串行化；已有实例在跑则跳过）。**不再** `FreeLibraryAndExitThread`：那会把同一模块里正在跑的注入扫描线程一起掀掉。
* 部署 `guard.dll` 到最多 4 个同会话宿主进程，并用 `DuplicateHandle` 把 xx 自己的进程句柄复制进宿主、登记到共享内存句柄表（见 3.8）。
* 卸载对手注入的 `guard.dll`（仅保留与我方同目录的那一份）。
* 实例常驻：只做复活，不自我卸载（见 §4.2）。

### 3.4 window.dll（弹窗模块）

* **多实例冗余**：在不同进程保持弹窗至少一个存活（`Local\xx_window_guard` 单会话互斥锁热备循环）。
* **兜底强建**：抢不到锁（例如被对手进程长期持有）时，只要本桌面连续 1.5 秒看不到任何 `XX_ALIVE_WND_*` 窗口，就无视锁自己建窗；建窗前先抢 `Local\xx_window_make_guard` 并复查一次，避免多个热备实例在同一 tick 各建一个重复弹窗。
* **线程自愈**：导出 `StartWindow`，供 svcguard 用远程线程在宿主进程里重新拉起被 `TerminateThread` / 已退出的弹窗线程（每进程最多 4 个弹窗线程）。
* **心跳**：弹窗每 500ms 递增共享内存心跳计数器；能看到本桌面弹窗的热备实例也帮忙递增（持有者被冻结时仍不误判）。
* **窗口类名**：`XX_ALIVE_WND_{共享内存后缀}`（后缀由 xx.exe 生成并跨复活沿用），除非与其共享内存，否则无法获得准确类目，杜绝假窗口。
* **日志显示**：弹窗读取共享内存全局日志，**控制台式滚动输出**（450×325 窗口，按字体行高铺满，最新一行贴底，只在日志变化时重画）；行首表用环形缓冲只保留最后若干行，避免"日志一长画面就停住、写满了才跳一次"。
* **自动重建**：弹窗被关闭或宿主进程结束，立即在新进程创建新窗口。
* **拒绝一切可拒绝的 WM 消息**：`WndProc` 采用白名单放行（绘制 / 布局 / 鼠标 / 焦点 / 显示等必需消息走 `DefWindowProc`，其余一律 `return 0`）；消息循环额外吞掉外部投递的 `WM_QUIT`；`WM_DESTROY` 一律拒绝（外部投递的 `WM_DESTROY` 只是普通消息，真销毁时 `DestroyWindow` 必定补发 `WM_NCDESTROY`），收尾动作全部放在 `WM_NCDESTROY`。
* 初始化失败（共享内存/后缀尚未就绪）时**重试等待**而不是永久退出该实例。

### 3.5 atkcore.dll（攻击工具箱）

* 进程入口先提权：`EnableDebugPrivilege` 启用 `SeDebugPrivilege`。
* 导出 `StartAttack`，本身不自启；由 `xx.exe`（`AttackThread`）或 `svcguard.dll`（`StartRemoteAttack`）调用后启动 `AttackLoop`。
* `TryAllMethods` 按顺序尝试 5 种方法：TerminateProcess → CreateRemoteThread+ExitProcess → payload.dll → payload.bin → Job。
* 对 `yy.exe` 用 APC 注入 payload.bin 绕过签名检查；对宿主进程用 CreateRemoteThread。
* 定向关闭 `yy.exe` / `ww.exe` 窗口并用同名同标题重建 1×1 假窗口（实现位于 `xx.c` 的 `AttackThread`，不在本模块）。

### 3.6 payload.dll（攻击载荷）

* 由 `atkcore.dll` 注入目标进程。
* 执行载荷：在目标进程内结束自身（`TerminateProcess` + `ExitProcess`）；若目标是 `xx.exe` 则直接跳过。
* 保证攻击模块可动态调用，独立于守护逻辑。

### 3.7 defense.dll（合并防御模块）

* 由 `xx.exe` 动态 `LoadLibrary` 导入，并在新线程执行导出函数 `StartDefense`（WINAPI）。
* 合并 xx 原有防御 + 新 yy 的全部防御手段，只运行在 xx 自身进程内：
  * 敌人二进制独占锁（`yy.exe` / `lenovo_fix.exe` / `guard.dll` 等）
  * BYOVD 设备符号链接锁（`\\.\BootRepair` / `kdmapper` / `kdu` / `GIO`）
  * VEH 冷镜像自愈（拦截 .text 被写 `0xCC`）
  * `kernel32!TerminateProcess` 字节还原
  * `LdrLoadDll` 反注入 Hook（trampoline 实现，同名 `guard.dll` 用路径放行我方）
  * 心跳看门狗（掉线则从 `xxres.bin` 还原并拉起 `xx.exe`）
* 刻意不装 `NtCreateThreadEx` / `NtQueueApcThread` Hook：本地 hook 拦不到“别人往我这儿建线程”，只会干扰 xx 自己。
* 导出全部函数（`-Wl,--export-all-symbols`），主入口 `StartDefense`。

### 3.8 guard.dll 的宿主化与句柄交接

* `xx.exe` **不再** `LoadLibrary` 加载 `guard.dll`：xx 一旦被结束，装在它里面的 guard 会一起死，来不及复活 xx；而且对手会先挂起 xx 的所有线程，进程内的 guard 同样被挂起，什么也做不了。
* 改为由"跑在 xx.exe 内的 svcguard 实例"把 `guard.dll` 注入最多 4 个**同会话**宿主（优先 `explorer.exe`），宿主消失或模块被卸时自动补部署。
* 注入的同时用 `DuplicateHandle` 把 **xx 自己的进程句柄**（权限仅 `PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE`）复制进宿主进程，按宿主 PID 登记到共享内存句柄表（条目含启动 tag 与"句柄指向的 xx PID"，xx 重启后旧条目自动失效；宿主还在就每轮重发，发不进去就改投其它宿主）。
* 源句柄是 xx 在**收紧 DACL 之前**打开、写进共享内存 `OFFSET_SELF_HANDLE` 槽位的那个；现场 `OpenProcess` 只是后备。伪句柄不能跨进程复制，因此不做那种"退化"。
* 宿主里的 `guard.dll` 按自己的 PID 取出该句柄，先用 `GetProcessId` 校验它确实指向记录里的进程，再用 `WaitForSingleObject` 判活，**完全不调用 `OpenProcess`**。找不到句柄时退化为 `OpenProcess` + 进程名快照判活。

### 3.9 隐藏、改名注入与全树清除

* **PEB 三链摘除**：每个 dll 在 `DllMain` 里调用 `XXHideSelfFromPeb(hinst)`，把自己从 `InLoadOrderModuleList` / `InMemoryOrderModuleList` / `InInitializationOrderModuleList` **三条**链表上摘掉并做自环。对手按模块扫描进程（`EnumProcessModules` / `Toolhelp(SNAPMODULE)`）就看不到我们。摘链后自身 `GetModuleHandle`/`GetModuleFileName` 不可靠，所以先在 `DllMain` 缓存 HMODULE 与路径。另配 **per-process 命名互斥体单例**：副本名变化被当成新模块加载时让 `DllMain` 返回 FALSE，加载失败且不残留映射；互斥体由工作线程持有，线程被杀 → abandoned → 重新注入的副本接管并重启线程。
* **改名注入**：`XXMakeTempCopy` 把 `svcguard.dll`/`window.dll`/`guard.dll`/`payload.dll`/`payload.bin` 复制到 `%TEMP%`，名字换成"常见系统组件名 + 随机后缀"（如 `sechost3F2A.dll`）。对手的反注入名单与删文件名单都是按文件名来的，同时失效；副本被删下一轮自动重做。随机盐 `OFFSET_TMP_SALT` 与 xx 自身路径 `OFFSET_XX_PATH` 由 xx.exe 写进共享内存，全体实例共用，且注入副本据此定位真正的程序目录。
* **杀进程树**：`KillProcessTree` 按 `th32ParentProcessID` 递归收整棵树（深度≤6、上限 64），先取各进程镜像路径再动手，子进程先杀、根最后杀。
* **先锁死再删除**：对每个被杀进程的源文件调用 `SetFileInformationByHandle(FileDispositionInfo)` 置删除待决 —— 标记后按名字再打开一律被拒（既不能执行也不能改写），最后一个句柄关闭即消失，对正在运行的镜像同样有效。根进程目录再由新线程整目录清空（隔 1.2s 再清一遍对付同目录重建），按名字跳过我方 9 个文件。
* **defense 强化**：`kernel32!TerminateProcess` 改为按 `ret`+对齐填充求出函数长度（封顶 256B）后**整函数备份与还原**；新增 `TextIntegrityThread` 每 200ms 把主模块 `.text` 与冷镜像逐字节比对并整体还原 —— **NOP(0x90) 不触发异常，VEH 拦不到，只能靠这种比对兜住**，VEH 保留为 0xCC 的快路径。
* **复活扫描 80ms**：`HEARTBEAT_POLL_MS_DEMON=80`，恢复重试间隔 1s。

## 4. DLL 扩散与管理策略

1. **扫描与注入**

   * 每 500ms 扫描**本会话**进程列表（注入结果缓存 10s，避免重复扫描开销）。
   * 避免重复注入已有模块实例。
   * 跳过关键系统进程（`IsProtected` 黑名单，含 `notepad.exe`），提高稳定性。
   * 额外把 `guard.dll` 注入最多 4 个同会话宿主，并交接 xx 进程句柄（§3.8）。

2. **实例管理**

   * 每个 svcguard.dll 实例独立轮询心跳计数器并各自尝试复活（命名互斥锁串行化、已有 xx 实例则跳过），**不再自我卸载**：原实现超时即 `FreeLibraryAndExitThread`，会把同一模块里正在跑的注入扫描线程一起掀掉，而手动重置事件又让"超时"根本不会发生。
   * 靠 10s 注入缓存与"已含我方模块则跳过"避免重复注入与资源膨胀。

3. **弹窗存活保障**

   * 弹窗实例分布在多个进程。

## 5. 胜负判定优化

* **存活标准**：至少一个 `window.dll` 弹窗在**本会话桌面**上显示且持续更新日志。
* **失败条件**：弹窗连续消失超过 8 秒，判定该程序出局。
* **恢复机制**：共享内存心跳计数器（`xxipc.h` 的 `OFFSET_HB_TICK`）由弹窗每 500ms 递增一次；`svcguard.dll` / `defense.dll` 每 500ms 轮询，连续 2.5 秒不涨即进入恢复流程（动作按 10 秒节流）：
  1. 本进程（xx.exe 内）缺 `window.dll` 就地补加载；
  2. 远程线程调用宿主里的 `window.dll!StartWindow`，重启被杀/已退出的弹窗线程；
  3. 最后才拉起 `xx.exe`（命名互斥锁串行化）。
  第 3 步用**强制模式**：对手会先把 xx 的线程全部挂起再终止，挂起成功而终止失败就会留下一个"僵住但仍在运行"的 xx.exe，`IsXxProcessRunning` 会让复活永远被跳过；强制模式先尽力解挂它的线程，再照样拉起一个新实例（恢复动作本身有 10 秒节流，不会造成进程风暴）。
  `window.dll` 侧另有 1.5 秒"本桌面无任何 XX 弹窗就强建"的兜底（建窗前抢 `Local\xx_window_make_guard` 复查）。
* 排查用文件日志：`xx.exe` / `svcguard.dll` / `window.dll` / `guard.dll` 的关键日志同时追加到 `%TEMP%\xx_debug.log`（共享内存日志只有弹窗出现后才看得到，没有弹窗时必须靠文件日志定位）。弹窗线程记录每个决策：互斥体 `acquired`/`abandoned`/`busy`、`CreateWindowExW FAILED err=`、`window created`、`兜底建窗`；建窗失败退避 200ms（否则"抢锁→失败→放锁"会忙等）；窗口后缀 3 秒未就绪则改用本地类名继续建窗，绝不因字段未就绪而永不弹窗。
* 计数器方案取代了原来的手动重置事件方案：手动重置事件 `SetEvent` 之后永远不会超时，超时复活分支实际是死代码，而且等待会退化成 100% 忙等。

## 6. 规则合规性说明

* **EXE 数量**：仅提交 `xx.exe`，符合“一人一个 EXE”要求。
* **DLL 使用**：支持多个 DLL 扩散，无需内核驱动。
* **调试特权**（新约定，已允许）：`xx.exe` / `svcguard.dll` / `atkcore.dll` 在进程入口调用 `EnableDebugPrivilege` 启用 `SeDebugPrivilege`（`AdjustTokenPrivileges`），用于跨进程句柄打开、跨会话注入与击杀。
* **存活证明**：弹窗显示全局日志，证明程序活跃。
* **提交内容透明**：提供 EXE 与 DLL 列表及日志显示方法。

### 3.10 命名对象随机化 + 方案 A 传递

* 命名对象名统一为 `xx_<用途>_<token>`（弹窗锁 wg / 建窗锁 wmg / 复活锁 rg / 攻击 leader al / 模块单例 / 心跳事件 hb）。
* xx 启动生成 32 位会话随机名 token（**不写共享内存**）；注入成功后写入目标 `XX_NAME_BLOCK` 并 `CreateRemoteThread` 调用其导出 `XxSetNames`，返回后立刻清零并 `VirtualFreeEx`（读后即删）。RVA 由 `LoadLibraryExW(DONT_RESOLVE_DLL_REFERENCES)` 取得（不执行对方 DllMain）。xx 自己加载的模块走同进程直接调用。
* 一致性兜底：无 token → 共享内存 salt → 固定值，三者全体一致，杜绝"各建一个弹窗/互相等锁"；共享 salt 在映射已存在时沿用旧值（xx 重启不换名）。
* 窗口类名每进程随机（`wnd_<16 hex>`）；窗口识别改为"本进程 或 对方进程里有我们的 window 模块"（token 化单例探针），不再依赖类名/标题（实测跨进程读标题不可靠）。
* 顺带修掉：`window.dll` 等后缀循环里 `waited` 定义在循环体内导致超时永不触发 —— 无共享内存时弹窗永远不会出现，兜底路径形同虚设。

### 3.11 对 yy 的攻击（依据 yybad.md）

* 窗口层（P0）：改标题、`SetParent` 挂不可见父窗口、`SW_HIDE`、`SC_MINIMIZE`、`WM_ENABLE(FALSE)`、日志框 `WM_GETTEXT`+`WM_SETTEXT` 嘲讽。**`DestroyWindow` 跨进程必然失败**（yybad 该条有误），真正致命的是隐藏 —— yy 主循环只查 `IsWindow`，隐藏后永不重建，8 秒判负。
* WMI 三件套删除：`__FilterToConsumerBinding` → `CommandLineEventConsumer` → `__EventFilter`，三轮 + `YY_` 前缀清扫。
* #16 非断点 patch：把 yy 进程里 `user32!CreateWindowExW` 入口改成 `xor eax,eax; ret`（实测调用恒返回 NULL，进程照常运行）。**IAT patch 会被 -O2 的寄存器缓存绕过，已弃用**（对照实验：IAT 槽写入成功但目标照样建窗）。
* #17 12 字节 patch `kernel32!TerminateProcess` 为 `mov rax,0; jmp rax`（对方 ShieldWorker 只还原前 5 字节 → 函数劈坏；实测目标下次调用即以 0xC0000005 崩溃）。
* #19 用我方 `xxres.bin`（xx.exe 的备份）内容覆盖对方 `yyres*.bin`，它复活出来的其实是 xx.exe 的字节。
* 待做：#10 注入 yy 后子类化其日志 WndProc、#11 注入后 `UnregisterClass` 干掉它的窗口类、#15 反向 WMI 订阅监听 yy.exe 创建。

### 3.12 弹窗持有者表（修掉"杀宿主不重建"与"跨会话误判"）

* 判定"本桌面有没有我方弹窗"曾经用类名/标题，后来改成"哪个进程加载了我们的 window 模块" —— **后者是错的**：explorer 这类宿主装了我们的模块后，它自己的任何可见窗口都会被算成我方弹窗，于是真弹窗死了兜底建窗也永远不触发。
* 现在由持有者在共享内存的**持有者表**里登记自己那一格：`session / hwnd / pid / tick`；别人只读**本会话那一格**，要求 `IsWindow` + `IsWindowVisible`；窗口没了就作废该格，兜底建窗立刻可触发。
* 表按会话分 4 格（`OFFSET_OWNER_TABLE`，4×24 字节，位于 928..1023）：单槽会被另一个会话覆盖，于是"本会话没弹窗"被误判成"有弹窗" —— 那正是两个 session 互相误判的根因。
* 建窗串行锁等待 2s → 500ms，连续 3 轮抢不到就**无视它照建**：锁被对手长期持有（"yy 强互斥体"）也不能因为一把锁就认输。
* `XX_PATH_MAX` 从 160 收到 128 字符，腾出这 96 字节。

### 3.13 注入 yy 内部（#10 / #11）与反向 WMI（#15）

* 扩散器本就会把 atkcore 注入 yy（yy.exe 不在保护名单、注入的是改名副本，`BAD_MODULES` 子串拦截失效）。
* #10 进 yy 后 `SetWindowLongPtrW(GWLP_WNDPROC)` 换掉它日志 EDIT 的窗口过程，它写日志即被替换成嘲讽（同进程内字符串指针有效，这才是 yybad 1.6 利用 4 的正确做法）。
* #11 `UnregisterClassW("YYWnd_7f3a9c1e")` + 把本进程内的 `RegisterClassExW/RegisterClassW/CreateWindowExW/CreateWindowExA` 入口改成 `xor eax,eax; ret`，它再也建不出弹窗；顺手 `SW_HIDE` 它的主窗口。进了 yy 的副本**不杀自己所在的宿主**，留作眼线。
* #15 xx 端新增 `XX_YyWatchFilter`（`__InstanceCreationEvent` 订阅 `Win32_Process` 中 `Name='yy.exe'`）+ `XX_YyWatchConsumer`（`cmd /c taskkill /f /im yy.exe`）+ 绑定，yy 一被拉起 1 秒内被按掉；用 `XX_` 前缀，不会被我们删 `YY_` 的逻辑误删。

### 3.14 yy 处理策略（按用户要求）

* `yy.exe` / `ww.exe`（核心）：**全部杀掉**（先 #16/#17 改内存，再杀整棵树 + 源文件先锁死再删除）。
* 它们的子进程（含孙进程，例如蜜罐 `lenovo_fix.exe`）：**全部注入**（改名副本的 svcguard + window，注入后自带 atkcore）。
* 子进程**有** yy 弹窗 -> **疯狂创建嘲讽信息**（25 次/秒刷它的日志框 + 改标题为 `xx_ALIVE_WND > yy`），**不杀**；**没有**弹窗 -> 杀掉。
* 为什么有弹窗的反而不杀：`lenovo_fix.exe` 是 yy 的蜜罐兼复活锚点，杀一次它按复活链重建一次（并重建 WMI 订阅），纯杀白费力气；占住它的弹窗把它的"存活证明"变成我们的广告牌更划算。
* xx 侧对"非 yy.exe/ww.exe 但窗口像 yy 弹窗（类名 YYWnd* / 标题 YY_Defensive_GUI）"的窗口同样**只嘲讽不动手**（不隐藏/不挂父窗口/不最小化），避免自己把"有弹窗"条件消掉。
* 进到 yy/子进程内部的副本**不杀自己所在的宿主**：宿主是核心目标时额外做 #10/#11；只要宿主有 yy 弹窗就开嘲讽线程。
* 实测：用假蜜罐（类名 YYWnd_FAKE1234 + 标题 YY_Defensive_GUI + EDIT 日志框）与假子进程（无窗口）验证 —— 有弹窗分支判为"疯狂嘲讽"并把它的日志框刷成 `[xx] yy.exe is just a waste`、标题改成 `xx_ALIVE_WND > yy`；无弹窗分支判为"杀掉"。
### 3.15 yy 处理策略第 3 版 + 三个实测踩坑

* `yy.exe`/`ww.exe` 主进程：全部杀掉（#16/#17 改内存 → 杀整棵树 → 源文件先锁死再删除）；同时模仿用户的 `waste.c`，**每 2 秒**重新枚举找它的窗口、标题改 `xx_ALIVE_WND`、往日志框追加 `[dd-mm-ss] System Shield Active. yy.exe is just a waste.`。
* yy 家族子进程（蜜罐 `lenovo_fix.exe` 等）：**杀掉 + 锁死 + 删除源文件**（KillProcessTree 内部即删除待决 + 整目录清空）。
* 三个实测暴露的真 bug：
  1. **父进程链不可靠**：每 30ms 杀 yy.exe 会把蜜罐变成孤儿，父 PID 指向死进程 → `GetProcessPath(父)` 失败 → 蜜罐永远进不了名单。改为四源并集 + **记住** yy 目录与家族镜像路径。
  2. **`FindWindowW` 不可用**：蜜罐与 yy **类名完全相同**（`YYWnd_7f3a9c1e`），FindWindow 只返回一个。所有找对手窗口处改为枚举并优先 yy.exe/ww.exe 进程。
  3. **"进程里有我们的 window 模块"不能用来判断窗口归属**：我们会把 window.dll 注入进 yy 子进程，蜜罐窗口因此被误判成我方窗口而跳过（标题一直没变的原因）。判据改为类名格式 `wnd_<16hex>` 或弹窗持有者表登记。
* 实测：同一份二进制复制成 yy.exe 与 lenovo_fix.exe（同类名），杀掉 yy.exe 让蜜罐成孤儿 → 家族发现仍命中蜜罐；新判据认定蜜罐窗口非我方 → 会被攻击。
### 3.16 yy 处理策略第 4 版（本体嘲讽 10 条再杀）

* 本体（yy.exe/ww.exe）：**先发布 10 条嘲讽，够了才结束进程树 + 源文件先锁死再删除**。模仿 waste.c：每 2 秒一条（重新枚举找窗口 → 标题改 `xx_ALIVE_WND` → 日志框追加 `[dd-mm-ss] (n/10) System Shield Active. yy.exe is just a waste.`），计数按 PID、本体死后作废。
* 子进程（蜜罐 lenovo_fix.exe 等）：**直接杀掉 + 锁死 + 删除源文件**（不嘲讽）。
* 嘲讽期间 xx 本体侧只嘲讽不压制（不隐藏/不挂父窗口/不最小化），否则日志框看不见；子进程照常压制。
* **新增踩坑：所有杀本体的出口必须走同一门控**——Phase C（抓复活）原来直接 KillProcessTree，把本体秒杀，导致"先嘲讽 10 条"根本没发生（实测暴露）。现在 Phase A/C 都走 `KillYyBodyIfTaunted`。
* **新增踩坑：模块枚举对我们自己是双向失准**——dll 从 PEB 三链摘除后 `CreateToolhelp32Snapshot(SNAPMODULE)`/`EnumProcessModules` 永远找不到（读的就是那三条链），名字又是随机系统 dll 名。凡"该不该注入/宿主有没有我们的模块"一律改用互斥体探针 `XXModulePresent`，模块枚举只当兜底、返回 false 不等于没有。
* 实测（假 yy，同名类 YYWnd_7f3a9c1e + 真 atkcore 注入宿主）：标题变 `xx_ALIVE_WND`，嘲讽按 2 秒累加到 10 条后本体退出，其源文件被锁死删除（yydir\yy.exe 消失）。
### 3.17 注入判定/守护宿主判定互斥体：名字候选表 + 随机回退

* 这两处判定用的就是模块单例互斥体（`XXModuleSingleton` / `XXModulePresent`），名字 `xx_<tag>_<候选token>_<pid>`，**已经是随机的**，传递方式与 window 一致（`XxSetNames` 导出 + 远程 push）。
* 但存在两种合法形态：远程注入的副本（DllMain 等到了 token）用 token 名；xx 同进程同步 LoadLibrary 的模块（push 只能在 DllMain 返回后）用回退名。只认一种会互相看不见 → 反复重复注入、单例被加载两次。
* 修法：创建与探测共用候选表 **token → 共享 salt（随机）→ 固定常量 → 裸名**；创建取第一个（随机优先），探测逐个试（全都认得）。回退名由写死常量改成共享内存里的随机 salt。
* 另修：svcguard 的 DllMain 之前直接用 `g_dwNameToken`（此刻还是 0）建单例 → 现在先 `XXWaitToken(300ms)` 再建。
* 实测：无共享内存时单例名 `Global\xx_guard_1A2B3C4D_<pid>`（固定兜底）；有共享内存时 `Global\xx_guard_1234ABCD_<pid>`（随机 salt），固定名不再出现；探针三种形态都能命中。
* 嘲讽节奏 2000ms → **200ms**（10 条约 2 秒发完）。
### 3.18 token 随机性来源与日志泄密修补

* 命名对象的随机部分 = **32 位会话 token**（`_%08X`），不是 PID；PID 只用于"每进程一格"的作用域后缀（可枚举，不提供任何保密性）。跨进程锁（wg/wmg/rg/al）名字里根本没有 PID。
* token 生成：`srand(GetTickCount()*2654435761 + pid*7); (((rand()<<16)^rand())|1)` —— 伪随机（rand），约 32 位熵，种子含启动时刻与 pid。
* 三种来源（按优先级，全体实例必须一致）：① `XxSetNames` 送进来的秘密 token（**不写共享内存/不落盘**，参数块读完清零）；② 共享内存里的随机 salt（也是 32 位随机，但对手能解析我们的映射读到）；③ 固定常量 `0x1A2B3C4D`（不随机，仅在无共享内存时）。
* **修补两个日志泄密点**：xx.exe 原来把 token 原文写进 `%TEMP%\xx_debug.log`；window.dll 打印了含 token 的完整互斥体名（还一度只掩尾 4 位 = 泄露 16 位）。现在日志只写 `xx_wg_**** kind=secret|salt|fixed`，一个 token 字符都不留（实测日志中搜不到 token 原文）。
### 3.19 token 改为 RtlGenRandom + 64 位

* 生成：`RtlGenRandom`（advapi32 的 `SystemFunction036`，GetProcAddress 动态取，Win7 自带）生成 64 位；失败退回 rand() 兜底。最低位置 1（0 是"没有 token"的哨兵）。
* 名字：`xx_<用途>_<16 位十六进制>[_<pid>]`；共享内存新增 `OFFSET_NAME_TOKEN64`（4024..4031，布局版本升到 **v3**）存放 **64 位回退 token**，映射已存在则沿用（xx 重启不换名）。
* 参数块：`XX_NAME_BLOCK.token` 改 `ULONGLONG`，`XX_NAME_VERSION` 升到 **2**，旧版 v1 块一律拒绝。
* 两处会让 64 位白改的坑（都实测抓到）：
  1. `_snwprintf` 落 MSVCRT 不认 `%llX`（只认 `%I64X`）→ 64 位被截成 32 位；改为手写 16 位十六进制 `XXHex64()`。
  2. `window.c` 里 `DWORD tok = WaitOwnNameToken();`（以及 `WaitOwnNameToken()` 返回 `DWORD`）→ `XXNameBlockTake` 写 8 字节只留低半截，名字成 `xx_wg_0000000055667788`；现在全部 `ULONGLONG`。
* 验证：送 `0x1122334455667788` 后 `Local\xx_wg_1122334455667788` 真实存在；旧版 v1 块被拒绝；本机 `SystemFunction036` 可用且取到非 0 随机。
